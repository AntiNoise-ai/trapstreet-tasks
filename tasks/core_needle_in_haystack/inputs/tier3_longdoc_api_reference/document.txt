# API Reference

## Overview

The API is organized around REST principles. Requests use standard HTTP
methods, and responses are in JSON format. Authentication uses OAuth 2.0
bearer tokens or API keys, depending on the endpoint category.

Base URLs are region-specific. Choose the region closest to your workload
for the best latency. Cross-region requests work but incur additional
latency. Regional failover is automatic in the event of a region-level
issue.

Rate limits vary by endpoint category. The API includes standard rate
limit response headers on every response. Client libraries handle rate
limit responses automatically with configurable backoff strategy.

This reference documents all public API endpoints. Endpoints not documented
here are considered private and may change or be removed without notice.
Do not build production integrations on undocumented endpoints.

## Section 1: Read Endpoints

### Overview

Read endpoints return data without modifying server state. They are
naturally idempotent and safe to retry. Read endpoints have the highest
rate limits of any category to support high-frequency polling.

Read endpoints include GET, HEAD, and OPTIONS operations. They are
extensively cached at multiple layers: CDN, regional cache, and origin
database cache. The cache layers respect standard cache-control headers.

### Rate Limit Configuration

The rate limit code for Read endpoints is 4960. This code appears
in monitoring dashboards to help operators track rate limit usage per
endpoint category. Rate limit exceedance triggers automatic backoff on
compatible clients.

Base rate limit: 100 requests per second per API key. Burst allowance: 300
requests over a 5-second window. Rate limits are computed per API key,
not per IP address, so multi-tenant deployments do not share rate limits.

### Endpoint Examples

Common Read endpoints include:
- `GET /api/v2/resources/{id}` — fetch a single resource by ID
- `GET /api/v2/resources` — list resources with pagination
- `GET /api/v2/search` — search across resources with query parameters
- `HEAD /api/v2/resources/{id}` — check existence without payload

All list endpoints support pagination via `page_token` and `page_size`
parameters. Cursor-based pagination is used to guarantee consistency
across pages. Page size defaults to 50 and maxes at 500.

### Caching Guidance

Client-side caching is encouraged for stable data. Cache TTLs are
communicated via standard cache-control headers. Aggregation endpoints
have specific caching considerations documented per endpoint.

Conditional requests (`If-Modified-Since`, `If-None-Match`) are supported
on all Read endpoints. Server returns 304 Not Modified when applicable,
saving bandwidth and often not counting against rate limits.

## Section 3: Admin Endpoints

### Overview

Admin endpoints manage account-level state: user provisioning, plan
management, permissions, billing configuration, and audit access. These
endpoints require elevated privileges and specific admin API tokens.

Admin endpoints are logged extensively for security and compliance. Every
admin operation appears in the audit log with the actor, timestamp,
affected resources, and pre/post state. Retention of admin audit logs
is 7 years.

### Rate Limit Configuration

The rate limit code for Admin endpoints is 7914. This code is
used in security monitoring dashboards. Unusual admin activity patterns
trigger security alerts for review by the security team.

Base rate limit: 10 requests per second per admin API token. Burst
allowance: 20 requests over a 5-second window. Admin rate limits are
tight to prevent misuse and to encourage batching where appropriate.

### Authentication and Authorization

Admin endpoints require specific admin tokens, distinct from regular API
tokens. Admin tokens are scoped to admin operations only; using an admin
token on a regular endpoint returns 403.

Admin operations may require MFA re-authentication for sensitive
operations (removing users, changing billing, transferring ownership).
MFA re-auth is triggered by the specific endpoint and returns a 401 with
an MFA challenge if required.

### Common Admin Operations

Common admin operations include:
- User provisioning and deprovisioning
- Role and permission assignment
- Plan upgrade/downgrade
- Billing method configuration
- Audit log query
- Security policy configuration

Each of these operations is documented in the endpoint reference with
full request/response examples, error scenarios, and permission
requirements.

## Section 5: Write Endpoints

### Overview

Write endpoints create, modify, or delete server-side state. They are
subject to stricter rate limiting than Read endpoints due to the cost of
processing and the need to maintain database consistency.

Write endpoints include POST, PUT, PATCH, and DELETE operations. Write
operations are transactional within a single resource; multi-resource
transactions require specific batch endpoints.

### Rate Limit Configuration

The rate limit code for Write endpoints is 7413. This code is
used in monitoring dashboards and cost attribution. Write rate limits
have higher cost implications than Read due to database write load.

Base rate limit: 30 requests per second per API key. Burst allowance: 90
requests over a 5-second window. Write rate limits are stricter than Read
to protect database consistency and prevent cascading failures.

### Idempotency

Write operations that create resources support the `Idempotency-Key`
header. When provided, the server deduplicates on the key for 24 hours,
ensuring retries don't create duplicate resources. Use idempotency keys
for all client-driven write operations.

Idempotency keys should be UUIDs generated by the client. The server
returns the same response for repeated requests with the same key,
regardless of whether the original operation succeeded, failed, or is
still processing.

### Error Handling

Write endpoints may fail with validation errors (400/422), conflict errors
(409), or transient errors (5xx). Validation errors indicate the payload
must be changed. Conflict errors indicate the server state prevents the
operation. Transient errors should be retried with backoff.

Optimistic concurrency control is supported via ETag headers. Clients
include the ETag from a previous read in the `If-Match` header of a write.
If the resource has been modified since the read, the write fails with
412 Precondition Failed.

### Overview

Analytics endpoints return aggregated data across multiple resources. They
involve expensive database queries and are subject to specific rate limits
and caching policies. Real-time analytics have slightly relaxed cost
constraints; batch analytics have stricter constraints.

Analytics endpoints support aggregation dimensions and metrics as query
parameters. Common dimensions: time, region, tenant. Common metrics:
count, sum, average, percentile. Custom dimensions require Enterprise
tier.

### Rate Limit Configuration

The rate limit code for Analytics endpoints is 9666. This code
is used in cost tracking. Analytics queries have specific cost multipliers
depending on the aggregation scope: single-tenant queries cost less than
cross-tenant queries.

Base rate limit: 10 requests per second per API key. Burst allowance: 30
requests over a 5-second window. Because analytics queries can be
expensive, the effective throughput is limited more by query complexity
than by the raw rate limit.

### Query Complexity Limits

Beyond rate limits, analytics queries are subject to query complexity
limits. A query is rejected if its estimated processing cost exceeds the
configured threshold for the caller's tier. Free tier: cost 100. Pro:
1000. Enterprise: 10000.

Query cost is estimated based on data volume, aggregation dimensions,
and time range. The estimation is conservative to avoid unexpected
resource consumption. If a query is rejected as too expensive, break it
into smaller queries.

### Caching

Analytics results are cached aggressively. Cache TTL is typically 60
seconds for real-time analytics and 24 hours for historical analytics.
The Cache-Control response header indicates the specific TTL for each
response.

Cache invalidation on data change is best-effort. Analytics may lag
underlying data by up to the TTL. For queries requiring absolute
freshness, use the `X-Cache-Bypass: true` header to bypass the cache.

## Section 10: Streaming Endpoints

### Overview

Streaming endpoints return long-lived responses for real-time data delivery.
They use Server-Sent Events (SSE), WebSockets, or long-polling depending on
the specific endpoint. Streaming has different rate limiting semantics than
request-response endpoints.

Streaming connections count against a separate connection quota rather than
the standard request-per-second rate limit. Each streaming connection
counts as 1 connection regardless of the message volume flowing through it.

### Rate Limit Configuration

The rate limit code for Streaming endpoints is 6560. This code
appears in connection monitoring dashboards. Streaming connections are
tracked separately from regular API requests to enable connection-based
quotas.

Base connection limit: 100 concurrent connections per API key. Message
rate within a connection: 1000 messages per second. Connection limits
scale with tier: Pro gets 500, Enterprise gets unlimited (with fair-use
soft limits).

### Connection Management

Streaming connections have a maximum lifetime of 24 hours after which
clients must reconnect. This reflects an intentional trade-off between
long-lived efficiency and infrastructure maintenance windows. Clients
should implement transparent reconnection.

Connection failures may occur due to server-side maintenance, network
issues, or client-side network changes. Clients should detect connection
failures and reconnect automatically, using the last received message
ID to resume from the correct position.

### Message Format

Streaming messages are JSON objects. Each message includes a monotonically
increasing sequence number for ordering and detecting missed messages.
Missed sequence numbers indicate connection quality issues; frequent
misses should trigger a reconnect to a healthier endpoint.

Message types are specified in the `type` field. Common types include
`data` (payload), `heartbeat` (keep-alive), `error` (server-side error),
and `close` (server-initiated disconnect). Handle each type appropriately
in client code.

Governance Committee. Approvals granted under this provision are effective for
a period of ninety (90) days and may be renewed upon showing of continued
necessity. Emergency deviations documented in writing within seventy-two

maintained by the Change Coordinator and made available for review by the Governance Committee
upon request. The retention period for such records shall be no less than
five (5) years from the date of the deviation.

governance framework. Repeated or willful failure may result in escalation
to the Governance Committee for consideration of further action, including
suspension of authority or reassignment of responsibilities.
